# Keep decision records living: rewritten in place, deleted once they stop holding

- **Date:** 2026-10-24
- **Governs:** `plugins/the-blueprint/skills/adr/SKILL.md`, `plugins/the-blueprint/skills/adr/assets/adr-template.md`

Agents write the ADRs and are their main readers, and an agent acts on the record in front of it. The `adr` skill keeps
each ADR as the decision in force and lets git hold what it replaced, at the cost of an in-file audit trail cut to one
line per change.

## Decision

- **Rewrite in place.** A changed decision, a reversal included, is rewritten so the file reads as the rule in force. A
  replaced rule that a reader could propose again becomes a Rejected line.
- **Delete what stops holding.** An ADR whose question is gone, or answered by another ADR, is deleted — no tombstone,
  status, or supersession line. The deleting commit says what it retired, why, and where its content went.
- **History records why.** One dated line per rule change carries the reason the rule moved.
- **Topic identity.** Files are `<group>.<n>-<topic>.md` and the topic names the question, so a rewrite never renames
  the file. Numbers only increase, and a deleted tail number is taken again.
- **No proposals.** An ADR is written once the decision is made.
- **Two-step implementation.** A decision recorded before its code carries a pending line until the implementing change
  brings the ADR to what was built.
- **Authority.** Agents write, rewrite, merge, demote, and delete ADRs, take every reason from evidence, and stop and
  ask before reversing a decision their task did not change.

The skill states each rule in full: `plugins/the-blueprint/skills/adr/SKILL.md`.

## Why

- A stale document misleads agents: in the pre-registered surface-bench study, a stale doc drove the misled rate to
  68–100% across 5 models from 3 providers, and suppressed the agents' own verification (2026-06).
- An append-only set grows chains an agent has to replay: kartta's set reached 200 ADRs under heavy agent workloads
  (2026-10-24), and ameise found 33 of its 70 ADRs no longer held as written (2026-10-04).
- Revisions appended beside an unchanged Decision leave the text contradicting its notes: one public ADR carried eleven
  dated revisions next to the Decision they replaced (2026-10).
- A History line in the file shows at a glance how often a rule moved, which git shows only on request.

## Consequences

- The in-file audit trail is one line per change, and the full wording lives in git. Accepted.
- Two branches that rewrite one ADR conflict, where two new files would not. Accepted.
- A link from outside the repository to a deleted ADR breaks; `git log -1 -- <path>` finds the deleting commit.
  Accepted.
- Tools and readers that expect Nygard statuses find none. Accepted.

## Rejected

- **Append-only records with supersession**, the form Fowler (2026-03-24), AWS, and Azure (2026-04) state — superseded
  ADRs stay findable, and agents follow them.
- **A new ADR for each reversal** — grew kartta's set under agent workloads; a rewrite keeps one file per question.
- **Tombstones for retired ADRs** — pile up in the tree and in the index.
- **History in git only** — gives no at-a-glance signal of a rule that keeps moving, and agents rarely query git before
  they act.
- **Proposals in the ADR directory** — agents follow what is in front of them, and proposals linger: one project's five
  sat `Proposed` for a month.
- **Filenames that state the decision** — a rewrite would rename the file or leave its name stating the old answer.

## Revisit if

A controlled comparison shows that append-only records mislead agents no more than living ones. Confidence medium: the
evidence is one benchmark of documentation in general plus practitioner reports, and no head-to-head study of ADR
lifecycles existed on 2026-10-24.
